## Home, entry and navigation

`onPartnershipClick` passes from `QuickActions` through HomeScreen, HomeRoute, and HomeNavigation to EkataYanNavHost. The action sits immediately after Group Hub and opens `PARTNER_ENTRY_ROUTE` (`business_partner/entry`). The quick-action row scrolls horizontally on narrow screens.

The entry uses existing travel imagery and the existing logo. Traveller opens the access-denied dialog with an Access Denied heading, the requested message, and exactly two actions:

- **Go Back:** dismisses the dialog and remains on Partner Entry.
- **Cancel:** dismisses it, navigates to the existing `HOME_ROUTE`, and pops the partner routes above normal Home. Back does not reopen the popup.

Business Partner opens `business_partner/step/1`. Steps 1–5 are individual destinations generated by `partnerStepRoute(step)`. Back traverses the preceding step. Step 5's Back to Home uses the same normal-Home exit callback.

All destinations are registered through `businessPartnerScreens` in the existing NavHost. There is no additional NavHost. Screen composables receive state and callbacks rather than a NavController.

## Shared state and onboarding

A single Hilt-created `BusinessPartnerViewModel` is scoped at the existing navigation-host level, following the Wishlist/Group Hub pattern. Its `LocalBusinessPartnerRepository` exposes one immutable `StateFlow<BusinessPartnerState>`.

- Step 1 stores one `profile.businessType`; selecting a category replaces the previous selection. Next is disabled until selected.
- Step 2 stores business name/category, email, phone, address, city, district, country, owner/manager name, contact email, contact phone, and an optional location label. Required fields, email syntax, and practical phone syntax are validated. These same fields are editable in the existing profile form.
- Add Location opens an editable local-label dialog. No map SDK is used.
- Step 3 requires a description (up to 500 characters) and at least one business image. An optional logo uses the existing single-image picker.
- Business hours are seven `BusinessHours` records, each with day, Open/Closed, and integer opening/closing minutes. A styled dialog uses Material `TimeInput`; overnight closing is explained.
- Social links are a list of `SocialLink(platform, url)` values. Each platform can be added, edited, or removed. Empty entries are removed when Done is pressed.
- Step 4 stores `Map<DocumentType, BusinessDocument>`. Registration and Owner/Manager ID are required; supporting documents are optional. The privacy note states the verification purpose and explains the local-only demo.
- Submit validates all four preceding steps and sets the local submitted flag. Step 5 explicitly explains that this is a local demo, with no review request sent.

Login is a lightweight frontend screen. It accepts a syntactically valid email and non-empty password, clears the password after continuing, and opens the dashboard. It does not authenticate an account. Returning to login does not reset locally edited/deleted listings.

## Images and documents

Business and listing photos use `ActivityResultContracts.PickMultipleVisualMedia` with ImageOnly. The profile logo uses `PickVisualMedia`. Add Photos is a plus/text control with no adjacent photo icon.

Returned URI strings are deduplicated and stored in the shared state (or the shared listing/profile draft). The preview strip allows more selections and individual removals. Existing demo listing images can also be removed/replaced. Profile-logo selection updates the dashboard and profile immediately.

Documents use `ActivityResultContracts.OpenDocument`, accepting PDF, images, Word, and OpenDocument text files. The display filename is read from `OpenableColumns.DISPLAY_NAME`. Each document supports Replace and Remove. Read access is retained where supported, with guarded permission handling and an error dialog for unreadable documents.

No broad storage permissions, uploads, or image-loading dependency were added. URI decoding is off the main thread and size-bounded; ViewModel state contains no bitmap data. Android's own system-picker UI retains the operating system's styling.

## Partner dashboard and bottom navigation

`PARTNER_HOME_ROUTE` (`business_partner/home`) is distinct from normal `home`.

The dashboard shows the current business name and logo, summary statistics, notifications/help dialogs, and working quick actions for Listings, Bookings & Inquiries, Business Profile, and Analytics.

The partner-only bottom bar has Home, Listings, Bookings, and Profile. Its Home action always opens the partner dashboard. Selection is derived from the active route. Tab navigation pops back to the partner dashboard before navigating, avoiding duplicate tab stacks. Normal user bottom navigation is unchanged.

## Listings

The repository seeds three demo listings with existing local imagery: a sea-view room, Yala safari, and camping rental. Counts derive from the actual local list rather than displaying a misleading fixed listing total. Demo views total 245 and inquiries total 48.

- Listings use `LazyColumn` and one reusable listing card.
- All, Rooms, Activities, Rentals, Dining, Transport, Vacation Rental, and Other filters use `listingFilter` and category values. Gear and equipment share the rental form; transport and vacation properties have distinct forms.
- Add New initializes one shared `ListingDraft`, using the selected business type to choose a default category and the profile location as default location.
- The same form handles creation and editing: title, description, positive finite price, custom pricing unit, category, status, location, photos, terms, structured category-specific fields, and availability. Monetary display preserves cents. Optional service fields validate supplied counts, quantities, deposits, and 24-hour times. Only fields relevant to the saved category are committed.
- Edit prefills the draft from the selected ID. Save replaces that listing while retaining its metrics; Back discards the draft.
- Save of a new listing inserts a UUID-backed item and resets the filter so it is visible immediately.
- Each card has an independently controlled menu: View, Edit, Change Status, and Delete.
- Status can be Active, Inactive, or Draft, with distinct badges.
- Delete is available from the list menu and details screen, reuses one confirmation dialog, and removes only the selected local listing. Details deletion returns to My Listings without keeping the deleted detail destination in the stack.
- `PartnerListingDetailsScreen(listingId)` resolves the item dynamically from shared state. Editing reflects in both details and list screens. Details show both existing resource and selected URI images, availability, category-specific information, status, terms, and edit/delete actions.

## Bookings, profile and analytics

Bookings use a `LazyColumn`, shared local records, and All/Pending/Confirmed/Completed/Cancelled filters. Records display booking date, requested service date, and guest/item quantity in addition to existing identity, amount, status, and inquiry text. View opens a styled detail popup. Confirm and Decline update pending bookings; confirmed bookings can be marked complete or declined. Completed/cancelled bookings cannot be transitioned again.

Profile displays identity, type, contacts, address, location, description, photos, hours, links, and demo verification status. Edit Profile uses a shared draft; Save validates and commits it and Back discards ordinary field edits. Profile-logo changes are immediate across identity areas, including when selected from the edit screen.

Analytics uses local cards and progress bars derived from shared listings/bookings. Listing additions, deletions, status changes, and profile changes propagate through the single state source. No chart library or backend analytics is used.

## Styling and persistence

All partner inputs explicitly use black text, including password, time input, links, and listing price. Partner screens adapt the existing EkataYan colors and Material typography, with navy headings, blue buttons, light backgrounds, and rounded cards. Forms scroll and respect safe-drawing/keyboard insets without a second IME-padding layer.

App-owned dialogs reuse `WishlistPopupSurface`; overflow menus use the same light-blue border, white background, dark text, and rounded shape. The normal app theme is not changed.

Data survives navigation and configuration changes while the host ViewModel lives. It does **not** survive process death or app restart. Restored protected partner routes with no session state redirect to Partner Entry. Persisted URI permission does not itself persist profile/listing data.

Everything remains frontend-only: account creation, login, application submission, verification status, images/documents, listings, booking actions, notifications, and analytics. A future data implementation can replace the local store and ViewModel integration without changing the screen callback contracts.

### Availability and access limits

Availability supports one optional inclusive date range and optional comma-separated daily HH:mm slots for activities. Dates/slots are validated but do not reserve stock, block bookings, enforce capacity, or calculate prices. Category-specific information is optional; malformed supplied numeric/time values prevent saving. Zero inventory is allowed to describe sold-out services. Dates left blank are explicitly shown as not set.

Traveller selection is denied at the UI boundary, and workspace routes require the local demo login state. This is not production role authorization: the preserved demo login accepts a valid email and non-empty password, and there is no backend account/verification system. Map selection, uploads, actual reviews and cross-restart persistence remain unavailable.
